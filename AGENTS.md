## Project notes

- Setup, scripts, environment variables, routes and layout: see README.md.
- Runtime is Node.js 24 LTS (`.nvmrc` is `24`, `engines.node` is `24.x`, matching Vercel). Don't use Node APIs newer than v24; reference: https://nodejs.org/docs/latest-v24.x/api/ (append `.md` to a module page for Markdown).
- TypeScript stays on `~6.0.x`: typescript-eslint 8 (pulled in by eslint-config-next) supports only `>=4.8.4 <6.1.0`, and TypeScript 7.0 ships no JS compiler API or tsserver. Don't upgrade to 7.x until typescript-eslint supports it (typescript-eslint/typescript-eslint#10940).
- Code style: tabs, single quotes, no semicolons, `@/` imports, default-exported components, named re-exports in barrels. ESLint forbids namespace imports (`import * as`).
- Server Components by default; add `'use client'` only at the entry of an interactive subtree. In Server Components, render Motion elements through named imports from `motion/react-client` (for example `import { div as MotionDiv } from 'motion/react-client'`).
- Code used by `/links` and `/links/schedule` imports shared primitives and hooks by file, not through barrels, to keep those routes' client JS small.
- Those two routes enter with `EntranceItem` (`src/components/motion/EntranceItem.tsx`, a CSS animation), not a Motion mount animation: Motion prerenders its hidden pose as an inline `opacity: 0` that only hydration lifts, so the page stays blank until its scripts run. Keep Motion there for what needs state (the booking steps).
- The home intro (`src/components/IntroGate.tsx`; its mark `src/components/LoadingLogo.tsx`, a Server Component; `IntroGate.module.css`; times in `intro` in `src/lib/animations.ts`) paints from the HTML: the mark's entry plays in CSS from the first paint and moves only transforms and opacity on boxes, so nothing done under it (hydration, the sky's start, its walk over the copy) can stall it. Under the loader the page is laid out and hydrated but unseen and still (`data-intro-phase` and the "Home intro" block in `globals.css`), never `display: none` and never remounted: nothing in `#intro-content` may change layout at the reveal, which changes visibility only, and nothing in it may set `visibility: visible` (undo `invisible` with `[visibility:inherit]`). A transition inside a size container (`@container`) in `#intro-content` names its properties, never `all` or `visibility`: Chromium 148 replayed the OtherProjects cards' `all` transitions from initial values under the loader at 1440 px wide (not at 393 px, where their grid's container query doesn't match), so their `visibility` ran from `visible` and the hidden cards showed and took Tab focus for about 0.3 s. Elsewhere in `#intro-content` nothing changes `visibility` under the loader, so the `all` transitions on links, buttons, the headshot, the work tabs and the phone menu show nothing there. An entrance that plays as the page appears waits for `useIntroRevealed()`, never for its own mount; one that plays on scroll may run under the loader when a visit lands below the hero, which then shows that copy at rest. Home's root keeps `scrollbar-gutter: stable` for the whole visit, and the loader takes the sky host's `100vw` box, so neither the page's width nor the sky's changes at the reveal, whether or not the browser takes a stable root gutter out of `vw`. The sky finds and measures the copy from its mount, under the loader. Before the dusk its quiet zones take new copy at once, with no ease, since no star shows yet. Before the stars come out the sky's worker asks for frames only to build a landing scene the visit starts inside (`FrameState.preparing`), and that scene shows whole, with no ease (`MiamiStep.showing`). The loader leaves once its mark has played and held (`intro.hold`) and the page is ready: its fonts, the images on screen and every promise handed to `useIntroHolds()` (the sky hands it `SkyController.prepared`, which its worker settles with `prepared` once what the lift will show is drawn, and which mountSky settles at once where CSS hides the sky, as under forced colors). It waits for readiness no later than `intro.ceiling` after the page could first be seen (navigation start, a prerendered page's activation, or the first showing of a tab opened in the background, read from the `visibility-state` performance entries where the browser keeps them, as Chromium does; elsewhere a page visible when it has hydrated counts from navigation start and a hidden one from its next showing), and once it starts to lift, nothing still running for readiness moves the page. A URL fragment's target is put at the top under the loader once the fonts have loaded and once more as the loader starts to lift, the last moment it covers the page (a reload or a history traversal keeps the position the browser restored). It plays on a document load only: a client navigation into home (from /links or the 404 page) shows the page at once.
- `typedRoutes` is on: a literal `<Link href>` or router path that matches no route fails type-check. Write a path kept in data as `'/x' satisfies Route` (`Route` from `next`), and cast a runtime string with `as Route` only where it was checked that way.
- The home sky draws in a Web Worker (`src/components/sky/sky.worker.ts`), and everything that file imports ships in the worker's start-up chunk, apart from what is loaded with `import()`: `src/lib/sky` imports only its own files, and the worker's files in `src/components/sky` (`sky.worker.ts`, `renderSky.ts`, `renderFireball.ts`, `renderRadial.ts`, `skyAssets.ts`, `bitmap.ts`, `hazeRuntime.ts`, `miamiRuntime.ts`, `miamiArt.ts`, `renderMiami.ts`, `miamiAssets.ts`, `miamiPalmArt.ts`) import only `@/lib/sky/*` by file and each other. None of them uses React, `window`/`document`, the `@/lib` barrel or `@/lib/utils`. On the main thread, sky code imports only types and `@/lib/sky/color` from `src/lib/sky`.
- The landing scene's art, the code that bakes and draws it, is a chunk of its own: `miamiRuntime.ts` loads `src/components/sky/miamiArt.ts` with `import()` while the intro's loader still covers the page, as part of what the worker waits for before it says it has prepared (`miami.warm`), so its stall comes under the loader unless the loader lifts at `intro.ceiling` first (what is left of the load then holds the stars back, and after a network error the bundler's one retry can stall the dusk); under Save-Data, or when the sky starts after the intro or only once the loader has begun to lift, it loads as the page's end comes near (`STAGE.loadAhead`), and a page with no scene (SkyLanding switched off) never loads it. `miamiArt.ts` and the files only it reaches (`miamiAssets.ts`, `renderMiami.ts`, `miamiPalmArt.ts`, `miamiWater.ts`, `miamiWind.ts`, `miamiSkyline.ts`) are imported by the worker's other files for types only (ESLint enforces it) and reached through `MiamiArt`; code the scene needs before its bake (its stage, timing and tunables) stays out of them. A new file that only the art reaches joins both lists in `eslint.config.mjs`'s art block (`ignores` and the pattern), or a value import of it from the worker's other files passes lint and puts it in the start-up chunk. Any of the worker's other files that the art imports by value stays out of the start-up chunk's hoisted scope, reachable by module id, and so does every file that one imports by value in turn, each with an export list and namespace reads at its uses in the start-up chunk. So `toBitmap`, which the art shares with the star atlas and the nebula, lives in `bitmap.ts`, which imports nothing, and not in `skyAssets.ts`, whose imports would take the star code (`comet`, `radiants`, `meteors`, `fireball`) out of that scope with it. A classic worker runs the chunk with `importScripts`, which stalls it, so the first load is made under the loader; a load that comes later waits for a calm, settled moment (`MiamiStep.calm`), but goes when the bake is due if none has come, and at once when the scene is needed. A failed load, the warm's included, is tried again when the bake is due or the scene is needed, and a second failure leaves the night sky for the visit, with no error event.
- Worker canvas code never uses `ctx.filter`: Safari's `OffscreenCanvas` doesn't have it. Bake blur in float.
- Copy the sky stays quiet behind carries `data-sky-quiet` (the hero, Contact, the footer and the side rails: no bright stars on it; a shooting star behind the hero, Contact or the footer dims to what that copy's WCAG contrast can take, a faint glimmer at most, and no sky event lights the rails); keep the attribute when editing those components, and keep that copy and its ancestors free of static `transform` translations and of `opacity` below 1 at rest, because the sky measures net of every translation and reads contrast from `color` alone.
- Everything else in `main` is reading copy (`READING_SELECTOR` in `src/components/sky/mountSky.ts`): the sky measures every line, link, button and solid image there, plans nothing near it, leaves no light on it at rest and keeps stars clear of it, with no attribute to add. Keep it and its ancestors free of static `transform` translations, which the measurement takes out, and keep copy in the page's flow inside `main` or in a `data-sky-quiet` element. The sunset's sky is fitted to Contact's copy, not to reading copy: today's reading lines over the sky stand more than 600 px above Contact's top, over ground near navy, and read at least 5.6:1, but slate text with its bottom edge at Contact's top would read about 4.2:1 on a 2560x1440 screen and 4.0:1 on a 3840x2160 one, under the 4.5:1 it needs, so after adding or moving a section just above Contact, recheck the reading copy over the canvas with the DOM hidden, reading the ground under each line with the stars taken out (bright features narrower than about 5 px), since stars still shine beside each line, and between lines on a narrow screen.
- Every sky event (each kind of shooting star, with its wake, train, sparks and pieces, and each satellite) hangs on the sky: `drawTransient` draws it where the camera's scroll has carried it since its launch (`transientShift`, at `TRANSIENT_NEARNESS`, the brightest stars' nearness), so a scroll moves it with the stars and a page at rest leaves it where its plan put it. Read its light, and anything else about where it is, from the moved body, never from where its plan put it on the screen. The comet hangs with the faint stars (`BODY_NEARNESS`).
- With the landing scene on, no flight launches at the foot of the page (`DESCENT.eventStop`).
- The home page ends in a sunset over Biscayne Bay, drawn in the sky worker (the stage in `src/lib/sky/miamiStage.ts`, the draw in `src/components/sky/renderMiami.ts`, its tunables in `src/lib/sky/miamiConfig.ts`; art constants stay in the bake and draw files and the tower data in `src/lib/sky/miamiSkyline.ts`). Its copy stays readable by construction, not with a scrim: `stageFrom` fits the sky to every Contact rect's `headroom`; the sky and clouds are locked to the page, so a rect's ground never changes with scroll; anything brighter than the sky stays below the lowest Contact rect (clouds by placement, the sun by `sunGate` and `haloScale`, the far city by `STAGE.farFade`, the beacons by a gate of their own; a streak above the copy floor is darker than the sky where it is placed, and drifted into the darker sky toward the sides it can read up to about 0.008 L lighter, but never behind Contact's copy); water under the footer stays under `WATER.footerCap`; the rails sit under a wing, the scene falling off toward the screen's edge, that is fitted to the rails' own rects and is as strong as the brightest sky, cloud or water that can pass behind their copy needs (`WING`). After any copy change near the end of the page, recheck the contrast: hide the DOM, screenshot the canvas, and read the worst pixel behind each quiet rect at several scroll positions.
- `SkyLanding` (between Contact and the footer) is empty room for the sky's landing scene: keep it free of copy. No copy goes below Contact's top except the footer. It is also the scene's off switch (one line, then a redeploy): render null from it, or render it only when `VERCEL_ENV` is `preview` or `NODE_ENV` is `development` to keep it off production. With no landing the sky has nothing to fit, so it draws the night sky alone and the page loses the empty room above the footer.
- `SkyRect.headroom` assumes a navy ground, so light added on copy (the veil's ink) scales to 0 through the descent (`SceneLevels.inkShare`), and no sky event launches once `scene.descent` reaches `DESCENT.eventStop`. `eventFloorY` is the lowest canvas y an event may fly at. At normal contrast that stop keeps launches above it, and a flight already up when the page nears its end keeps its light off the band below it, as it does off reading copy, so that light fades out just above the floor, point by point. The comet, which stays through scrolling, does the same through its box: the band dims all of the comet as it nears the box, and the comet leaves once the band is within reach of it.
- `MAX_QUIET_RECTS` cuts flow rects from the end of the DOM, so footer rects go first, and `stageFrom` needs them: keep the count under it.
- The sky's pause control (`src/components/sky/SkyPauseButton.tsx`, in the navbar, state in `skyPause.ts`) is its WCAG 2.2.2 mechanism: it maps to the worker's `motion: 'reduced'`, and any new continuous sky motion must stop under it, the landing scene's included, and settle to its still pose through `driftGate.level`.
- The Hide/View control (`src/components/sky/SkyViewToggle.tsx`, state in `skyView.ts`) hides all of the home page's content, the navbar and its pause control included, so the sky shows alone; the control or Escape brings it back. It stands where a second pause control stood, one shown at a time: the right rail's first item from `md` up in windows taller than 386px, and the footer's, beside "Built by", elsewhere. Both are copy the sky measures (the rail's box shapes the sunset's wing, and the footer's is a footer rect the stage reads), so changing either box means the contrast recheck above. Hiding marks `<html>` with `data-sky-only` and every `data-sky-hide` element (the navbar's header, each rail's copy and line, `main`, and the footer's links and its "Built by" link) with `inert`, and those elements fade out and lose their visibility, never their boxes; showing takes the attribute away and sets nothing in its place. The fade's transitions apply only once the page shows (`#intro-content[data-intro-phase='revealed']`, in `globals.css` and on the navbar's header), so nothing of it transitions `visibility` under the intro's loader, where the control can't be pressed. Hide content no other way: a change of `display`, size or position moves the rects the sky measures and the landing stage with them. Their opacity of 0 while hidden is the one exception to the quiet-copy rule above. Content outside those elements needs `data-sky-hide` of its own, and the controls stay outside all of them. Never put `data-sky-hide` on an `a`, `button` or `img` in reading copy, or on an `a` that holds one: `mountSky` drops a reading box whose own opacity, or its link's, is under 0.5, and its copy observer doesn't watch attributes, so a box measured while hidden would stay missing after Show until the next measure. Under forced colors the content always shows: the store never hides it there and shows it again, `inert` gone, if they come on while it is hidden. The worker hears it as `{ type: 'copy', shown }`: while the copy is hidden its stars, flights and comet keep clear of the rails and of copy still on screen alone (rects `mountSky` marks `stays`: the footer's control), and the landing stage stays fitted to the copy as measured; when the copy shows again, flights and the comet answer to it at once and the stars and the glitter fade out of its way over `QUIET.ease`, which the content's 0.6s fade-in (`globals.css`) matches, and a Show while the hide's ease still runs turns that ease back where it stands (`adoptLayout`). The contrast rechecks above hide the DOM with an injected style, never with this control: hidden mode changes what the sky draws.
- The nebula (`src/lib/sky/nebula.ts`, the light the sky's `haze` level draws) is gas behind every star. Its light is a pure function of the drift clock (`camera.clock`) and its place a pure function of the scroll the camera has followed: `advanceHaze` in `src/components/sky/hazeRuntime.ts` composes it into the one bitmap of which `drawSky` blits a screen's worth, from the row `nebulaShift` gives; it has no frame demand or layer of its own, and it stops with the drift under the pause control, while idle and in a hidden tab. It hangs farther than any star (`NEBULA.depth`: nearness 0.2, against the faintest star's 0.24), so a scroll carries it up the screen more slowly than anything else, through the camera's spring, and it takes no share of the drift or the lean; keep every star, event and body nearer than it. While the sky is paused or under reduced motion it hangs at its place over the hero and only its level follows the scroll. Its field reaches below the screen as far as the scroll carries it while its light lasts (`nebulaStrip`), and its light recedes with the scroll (`SCENE.hazeHold`, `hazeRecede`, `hazeGone`): it is out past the first reading sections and at the page's end. Its light at any moment stays under a closed-form ceiling in white-equivalent and blue (`NebulaField.bound`). Retuning anything `bound` reads, `NEBULA.depth`, `CAMERA.scrollParallax` or `maxLag`, `SCENE`'s haze levels and fades, or moving the copy it sits beside, means sweeping that bound again, the field moved up by every shift the scroll can give it, under quiet copy (`INK_BUDGET.hazeReserve`) and under reading copy between the hero and Contact, which has no reserve: its rects keep events off it, not the nebula, and its slate body text keeps at least 4.8:1. `NEBULA`'s doc lists what needs a sweep and what is free. The sweep's tools aren't in this repo, so ask the user before such a change.
- Cache Components is not enabled: don't add `instant`, `'use cache'`, `cacheLife` or other APIs that require `cacheComponents`.
- Tailwind detects class names only in `src/` (`source("..")` on the import in `src/app/globals.css`), so class names written outside `src/` get no CSS. Keep plans and other docs out of `src/`: Tailwind reads Markdown and source files there unless git ignores them, so a word in a doc that names a utility the site doesn't use yet (`table`, `sticky`) can add CSS to the site.
- Verify every change with `npm run lint` and `npm run type-check` (it runs `next typegen` first, so generated route types are checked too). While `next dev` runs, use its MCP endpoint `/_next/mcp` (`get_errors`, `get_compilation_issues`, `compile_route`) instead of `next build`.
- If `next dev` or `next build` stops with a Next.js upgrade reminder, tell the user and rerun the command; don't upgrade Next.js without asking.
- Never POST to `/api/schedule/book`: it creates real Google Calendar events and sends real emails. To check the integration, GET `/api/schedule/slots?date=YYYY-MM-DD` for an upcoming bookable date (non-bookable dates return `[]` without calling Google). A 200 by itself doesn't show Google answered: the endpoint returns the static schedule from `src/lib/scheduleConfig.ts` when the `GOOGLE_*` variables are unset (silently) or when FreeBusy fails (logged as `[google-calendar] FreeBusy query failed`), so check the server log, and expect busy hours to be missing from the result.
- Never commit `.env*` files except `.env.example`.
