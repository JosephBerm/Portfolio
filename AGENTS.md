## Project notes

- Setup, scripts, environment variables, routes and layout: see README.md.
- Runtime is Node.js 24 LTS (`.nvmrc` is `24`, `engines.node` is `24.x`, matching Vercel). Don't use Node APIs newer than v24; reference: https://nodejs.org/docs/latest-v24.x/api/ (append `.md` to a module page for Markdown).
- TypeScript stays on `~6.0.x`: typescript-eslint 8 (pulled in by eslint-config-next) supports only `>=4.8.4 <6.1.0`, and TypeScript 7.0 ships no JS compiler API or tsserver. Don't upgrade to 7.x until typescript-eslint supports it (typescript-eslint/typescript-eslint#10940).
- Code style: tabs, single quotes, no semicolons, `@/` imports, default-exported components, named re-exports in barrels. ESLint forbids namespace imports (`import * as`).
- Server Components by default; add `'use client'` only at the entry of an interactive subtree. In Server Components, render Motion elements through named imports from `motion/react-client` (for example `import { div as MotionDiv } from 'motion/react-client'`).
- Code used by `/links` and `/links/schedule` imports shared primitives and hooks by file, not through barrels, to keep those routes' client JS small.
- The home sky draws in a Web Worker (`src/components/sky/sky.worker.ts`), and everything that file imports ships in the worker's start-up chunk, apart from what is loaded with `import()`: `src/lib/sky` imports only its own files, and the worker's files in `src/components/sky` (`sky.worker.ts`, `renderSky.ts`, `renderFireball.ts`, `renderRadial.ts`, `skyAssets.ts`, `bitmap.ts`, `hazeRuntime.ts`, `miamiRuntime.ts`, `miamiArt.ts`, `renderMiami.ts`, `miamiAssets.ts`, `miamiPalmArt.ts`) import only `@/lib/sky/*` by file and each other. None of them uses React, `window`/`document`, the `@/lib` barrel or `@/lib/utils`. On the main thread, sky code imports only types and `@/lib/sky/color` from `src/lib/sky`.
- The landing scene's art, the code that bakes and draws it, is a chunk of its own: `miamiRuntime.ts` loads `src/components/sky/miamiArt.ts` with `import()` as the page's end comes near (`STAGE.loadAhead`), so a visit that stays near the top downloads none of it. `miamiArt.ts` and the files only it reaches (`miamiAssets.ts`, `renderMiami.ts`, `miamiPalmArt.ts`, `miamiWater.ts`, `miamiWind.ts`, `miamiSkyline.ts`) are imported by the worker's other files for types only (ESLint enforces it) and reached through `MiamiArt`; code the scene needs before its bake (its stage, timing and tunables) stays out of them. A new file that only the art reaches joins both lists in `eslint.config.mjs`'s art block (`ignores` and the pattern), or a value import of it from the worker's other files passes lint and puts it in the start-up chunk. Any of the worker's other files that the art imports by value stays out of the start-up chunk's hoisted scope, reachable by module id, and so does every file that one imports by value in turn, each with an export list and namespace reads at its uses in the start-up chunk. So `toBitmap`, which the art shares with the star atlas and the nebula, lives in `bitmap.ts`, which imports nothing, and not in `skyAssets.ts`, whose imports would take the star code (`comet`, `radiants`, `meteors`, `fireball`) out of that scope with it. A classic worker runs the chunk with `importScripts`, which stalls it, so the load waits for a calm, settled moment (`MiamiStep.calm`), but goes when the bake is due if none has come, and at once when the scene is needed; a failed load is tried again when the bake is due or the scene is needed, and a second failure leaves the night sky for the visit, with no error event.
- Worker canvas code never uses `ctx.filter`: Safari's `OffscreenCanvas` doesn't have it. Bake blur in float.
- Copy the sky stays quiet behind carries `data-sky-quiet` (the hero, Contact, the footer and the side rails: no bright stars on it, and a shooting star behind it dims to what that copy's WCAG contrast can take, a faint glimmer at most); keep the attribute when editing those components, and keep that copy and its ancestors free of static `transform` translations and of `opacity` below 1 at rest, because the sky measures net of every translation and reads contrast from `color` alone.
- Everything else in `main` is reading copy (`READING_SELECTOR` in `src/components/sky/mountSky.ts`): the sky measures every line, link, button and solid image there, plans nothing near it and leaves no light on it, with no attribute to add. Keep it and its ancestors free of static `transform` translations, which the measurement takes out, and keep copy in the page's flow inside `main` or in a `data-sky-quiet` element. The sunset's sky is fitted to Contact's copy, not to reading copy: today's reading lines over the sky stand more than 600 px above Contact's top, over ground near navy, and read at least 5.6:1, but slate text with its bottom edge at Contact's top would read about 4.2:1 on a 2560x1440 screen and 4.0:1 on a 3840x2160 one, under the 4.5:1 it needs, so after adding or moving a section just above Contact, recheck the reading copy over the canvas with the DOM hidden, reading the ground under each line with the stars taken out (bright features narrower than about 5 px), since stars are drawn behind it.
- Farewell meteors fly only in the sky below the top of the highest quiet copy of the page's flow that is on screen (`planFarewell` in `src/lib/sky/meteorKind.ts`). With the landing scene on, no flight launches at the foot of the page (`DESCENT.eventStop`), farewell meteors included.
- The home page ends in a sunset over Biscayne Bay, drawn in the sky worker (the stage in `src/lib/sky/miamiStage.ts`, the draw in `src/components/sky/renderMiami.ts`, its tunables in `src/lib/sky/miamiConfig.ts`; art constants stay in the bake and draw files and the tower data in `src/lib/sky/miamiSkyline.ts`). Its copy stays readable by construction, not with a scrim: `stageFrom` fits the sky to every Contact rect's `headroom`; the sky and clouds are locked to the page, so a rect's ground never changes with scroll; anything brighter than the sky stays below the lowest Contact rect (clouds by placement, the sun by `sunGate` and `haloScale`, the far city by `STAGE.farFade`, the beacons by a gate of their own; a streak above the copy floor is darker than the sky where it is placed, and drifted into the darker sky toward the sides it can read up to about 0.008 L lighter, but never behind Contact's copy); water under the footer stays under `WATER.footerCap`; the rails sit under a wing, the scene falling off toward the screen's edge, that is fitted to the rails' own rects and is as strong as the brightest sky, cloud or water that can pass behind their copy needs (`WING`). After any copy change near the end of the page, recheck the contrast: hide the DOM, screenshot the canvas, and read the worst pixel behind each quiet rect at several scroll positions.
- `SkyLanding` (between Contact and the footer) is empty room for the sky's landing scene: keep it free of copy. No copy goes below Contact's top except the footer. It is also the scene's off switch (one line, then a redeploy): render null from it, or render it only when `VERCEL_ENV` is `preview` or `NODE_ENV` is `development` to keep it off production. With no landing the sky has nothing to fit, so it draws the night sky alone and the page loses the empty room above the footer.
- `SkyRect.headroom` assumes a navy ground, so light added on copy (the veil's ink) scales to 0 through the descent (`SceneLevels.inkShare`), and no sky event launches once `scene.descent` reaches `DESCENT.eventStop`. `eventFloorY` is the lowest canvas y an event may fly at; nothing reads it yet, because at normal contrast that stop and the scroll cancel already keep flights above it.
- `MAX_QUIET_RECTS` cuts flow rects from the end of the DOM, so footer rects go first, and `stageFrom` needs them: keep the count under it.
- The sky's pause control (`src/components/sky/SkyPauseButton.tsx`, in the navbar, in the right rail from `md` up, and in the footer wherever the rail shows none, state in `skyPause.ts`) is its WCAG 2.2.2 mechanism: it maps to the worker's `motion: 'reduced'`, and any new continuous sky motion must stop under it, the landing scene's included, and settle to its still pose through `driftGate.level`.
- The nebula (`src/lib/sky/nebula.ts`, the light the sky's `haze` level draws) is gas behind every star, a pure function of the drift clock (`camera.clock`). `advanceHaze` in `src/components/sky/hazeRuntime.ts` composes it into the one bitmap `drawSky` blits; it has no frame demand, camera offset or layer of its own, and it stops with the drift under the pause control, while idle and while hidden. Its light at any moment stays under a closed-form ceiling in white-equivalent and blue (`NebulaField.bound`). Retuning anything `bound` reads, `SCENE`'s haze levels and fades, or moving the copy it sits beside, means sweeping that bound again under quiet copy (`INK_BUDGET.hazeReserve`) and under reading copy between the hero and Contact, which has no reserve: its rects keep events off it, not the nebula, and its slate body text keeps at least 4.8:1. `NEBULA`'s doc lists what needs a sweep and what is free. The sweep's tools aren't in this repo, so ask the user before such a change.
- Cache Components is not enabled: don't add `instant`, `'use cache'`, `cacheLife` or other APIs that require `cacheComponents`.
- Tailwind detects class names only in `src/` (`source("..")` on the import in `src/app/globals.css`), so class names written outside `src/` get no CSS. Keep plans and other docs out of `src/`: Tailwind reads Markdown and source files there unless git ignores them, so a word in a doc that names a utility the site doesn't use yet (`table`, `sticky`) can add CSS to the site.
- Verify every change with `npm run lint` and `npm run type-check` (it runs `next typegen` first, so generated route types are checked too). While `next dev` runs, use its MCP endpoint `/_next/mcp` (`get_errors`, `get_compilation_issues`, `compile_route`) instead of `next build`.
- If `next dev` or `next build` stops with a Next.js upgrade reminder, tell the user and rerun the command; don't upgrade Next.js without asking.
- Never POST to `/api/schedule/book`: it creates real Google Calendar events and sends real emails. To check the integration, GET `/api/schedule/slots?date=YYYY-MM-DD` for an upcoming bookable date (non-bookable dates return `[]` without calling Google). A 200 by itself doesn't show Google answered: the endpoint returns the static schedule from `src/lib/scheduleConfig.ts` when the `GOOGLE_*` variables are unset (silently) or when FreeBusy fails (logged as `[google-calendar] FreeBusy query failed`), so check the server log, and expect busy hours to be missing from the result.
- Never commit `.env*` files except `.env.example`.
